01

索引与扫描

这里只用编号1、3、5、8四件商品，与上一天一样按id找行。扫描是依次访问候选并判断条件；索引是事先按某些列组织的查找结构，查询可利用它排除无关部分。

找id=8，假设扫描顺序是1、3、5、8，就要逐个判断。若查找结构记录“左页编号小于5，右页编号至少5”，8不可能在左页，直接去右页找。减少的工作来自这个排除依据，不是WHERE关键字变快了。

这张小图只解释怎样跳过，无意证明四行一定值得建索引。name索引提供的是名称定位信息，不能直接替price定位；需要大部分行时，扫描也可能更划算，第6天再比较成本。

02

B+树的层级与有序叶子

把刚才的范围安排成树：最上方的根节点记录分隔键5与两条子页引用，小于5去左页，否则去右页。子页引用也叫指针，表示下一步到哪个页，不是另一件商品。

底层不能再向下的节点叫叶子。左叶放编号1、3的项，右叶放5、8的项；一个索引项对应一个键值与它关联的记录信息。InnoDB主键叶子承载商品行，本图只露出id。节点放在页中：沿根到叶，实际是在取得这些节点所在的页。

找8时，比较8与5，进入右叶，再在其中找到8。查3至8时，先从根定位到左叶的3；3仍小于上界8，就沿叶子连接取5、8，到8后结束，不再把每个键从根查一遍。

这种内部节点可指向多个子页、叶子深度相同、叶子按键序相连的结构叫B+树，是一种多路、平衡的有序查找树。内部导航负责定位起点，叶子连接负责继续范围。索引内部有序不保证SQL输出顺序，需要排序仍写ORDER BY。

03

页容量、分叉与树高

扇出是一个内部节点能指向多少子节点。节点放在容量有限的页里；导航键与指针越宽，同页通常能放的导航项越少。

固定四片叶页L1至L4：根若能放四个子指针，可直接指向全部叶页；若只能放两个，就需要两个中间节点分别管理L1/L2和L3/L4。找同一片L4，前者经过根、叶两页，后者经过根、中间、叶三页。

节点覆盖更多范围时，相同数据规模通常可用较矮的树组织。内部节点不承载完整行，有利于留空间给导航；第5天的主键宽度也影响索引空间。

页大小与实际读盘

默认页通常为16KB。页跳数不等于磁盘读取次数，缓冲池命中可省去读盘。四个或两个指针不是实际容量。

04

B树、红黑树与Hash

B树也多路且平衡，内部节点可保存数据项，点查可能中途结束。红黑树用颜色规则控制高度，每个节点最多两个子分支，大量数据时通常需要更多层。

Hash按规则从键算到存放分组，这叫散列计算；分组叫桶，是一组存放位置。不同键3、5若映射到同一个桶A，就叫碰撞，仍要核对原键。桶号不保留键的大小顺序，无法像B+树叶子那样直接连续取范围。

MySQL中的使用

InnoDB常规索引用B+树；MEMORY可用Hash。InnoDB自适应Hash是内部优化，不是给普通表声明通用Hash索引。

03SQL短练习

排序、取前几行与去重

ORDER BY定义输出顺序；ASC升序（默认），DESC降序。LIMIT限制输出行数。价格可能相同，取前两名时可用id作第二排序条件，消除并列的不确定性。

SELECT id, name, price FROM products ORDER BY price DESC, id ASC LIMIT 2;
SELECT DISTINCT name FROM products;

DISTINCT删除所选列组合的重复结果。只选name，两件“水”合并；选name、price时，两种价格的水不会合并。它不修改原表。没有ORDER BY时不依赖偶然显示顺序；本日排序题会检查顺序，去重题只检查结果集合。

04理解自测

用自己的话回答，再对照参考解释。

1 / 索引减少的主要是什么工作？

查看参考答案

它用组织好的查找结构跳过不相关范围，减少读取、比较与处理。不保证所有查询都更快，也不是WHERE关键字本身。

2 / B+树内部节点和叶子各有什么作用？

查看参考答案

内部节点按键值导航到子节点；叶子保存索引项，并按键序连接。InnoDB主键叶子保存行数据。所有叶子深度一致。

3 / 为什么叶子相连对范围查询有帮助？

查看参考答案

可先定位范围起点，再按叶子键序继续遍历到上界，不必把每个目标都从根重新定位。SQL输出顺序仍需ORDER BY。

4 / Hash擅长等值，为什么不因此替代所有B+树？

查看参考答案

Hash桶不保留键大小顺序，不天然支持同样的范围及排序访问；碰撞与实现也有代价。B+树兼顾等值、范围和有序遍历。

5 / 无限增加分叉能否永远改善效率？

查看参考答案

不能。节点受页容量、键与指针宽度限制；页内查找、读写和维护也有代价。不能把树高当成固定三层。
