02今日主线

固定四个商品索引项，依次给出名称、价格条件，观察候选从四项变两项、再变一项。定位范围与筛选结果不是同一件事；有可用路径以后，还要比较它与扫描的工作。

01

联合索引与最左前缀

固定商品(奶,8,3)、(水,3,1)、(水,4,4)、(面包,5,2)，括号依次为name、price、主键id。INDEX(name,price)声明联合索引：先按name分组，同组再按price排序。图中“奶、水、面包”是显式教学顺序，不用它推断MySQL排序规则。

查询只给name='水'，整个水组连续，跳过奶和面包，候选从四项缩到两项。再加price=4，水组内价格有序，缩到(水,4,4)一项。最左前缀指从索引首列开始连续的一段，如(name)、(name,price)；它给出了这两次缩小的依据。

只给price=4时，四个价格分散在不同name组，并非全局价格顺序，这个普通定位模型需检查四项再筛出一项。改索引为(price,name)，price成为首列，才有连续的价格组可定位。

图里被跳过的项没有进入本例候选区；候选还要按完整条件判断，最终结果可能更少。WHERE中两个等值条件的书写顺序不改变索引定义。

范围与其他计划

前列用范围时，后列不一定继续缩小同一扫描区间，但仍可过滤或覆盖。跳跃扫描属于其他办法，不能背成缺首列就绝不读索引。

02

可定位条件与额外过滤

定位条件确定从哪里开始、到哪里结束；额外过滤判断已读候选要不要保留。结果一样，不代表读取范围一样。

普通name索引中，LIKE '水%'给出开头，可形成前缀范围；LIKE '%水%'还匹配饮用水，却不给相同起点，通常需要检查更多项。

price=4直接表达目标键；price+1=5要求计算后比较，通常不能照搬普通price索引定位。类型不匹配还可能隐式转换，即自动转成另一类型再比较。

不能当作失效口诀的情况

B+树也可包含NULL，IS NULL可用适当索引。OR可能用索引合并，函数索引或改写也可提供路径。不能直接定位与完全不读索引是两回事。

03

建索引的收益与维护成本

建索引权衡读取收益与维护成本。选择性描述条件缩小范围的程度：唯一id只剩一行，九成上架的标记则保留大部分。

大表高频查一件商品，定位收益可被大量请求重复利用；小表偶尔整体导出，扫描原本工作就少。二级路径若为大部分记录回表，还可能比扫描多做工作。

插入、删除要维护相关索引，修改索引列也要更新对应项；索引还占磁盘与缓存。因此结合频率、候选数量、取列和写入成本决定，而不是每列各建一棵树。

低基数与冗余索引

不同值少的低基数列仍可服务覆盖、排序或特定查询。核对约束和实际查询后，才判断相似索引是否冗余。

04

EXPLAIN与优化器选择

固定图中的四行商品与stock二级索引idx_stock，查询只取name，而name不在该索引项中。查stock=0，二级索引找到商品2，再用id=2回表取面包；扫描则检查四行，只保留商品2。改查stock≥0，四行都匹配，二级路径要四次取项、四次回表。

这个模型把一次取索引项与一次回表各算一份工作，扫描一行也算一份：找一行时2对4，取全部时8对4。它解释“能用索引不等于值得用”，不是测出的时间，也不是优化器实际成本公式。你选择哪条路径，图和手写计划就展示哪条；推荐另列，不替换你的选择。

EXPLAIN展示数据库准备怎样执行SQL，在查询前加EXPLAIN即可查看。图中的输出是路径对应的手写教学值，不是实际MySQL输出。

  1. type、key：ref与idx_stock表示本例等值索引访问；range表示范围访问；ALL与NULL表示扫描，没有选定位索引。
  2. rows：估计检查的行，不等于返回行数，也可能不同于实际。
  3. possible_keys：可考虑的候选；它有idx_stock而key为NULL，表示有候选却选了扫描。
  4. Extra：补充工作，如Using where表示过滤，不能仅凭字样判断好坏。
覆盖、条件下推与实际观测

Using index通常提示覆盖；Using index condition是索引条件下推，在靠近引擎访问处检查部分条件、减少取行，两者不同。真实成本还涉及页、缓存与统计。EXPLAIN ANALYZE实际执行查询，使用前要评估负载。

03SQL短练习

聚合：把多行汇成一个值

本SQL区四行stock是10、6、NULL、2。数所有行得到4；只数有已知stock的行得到3；把已知库存相加得到18。把一组行计算成统计值的函数叫聚合函数：COUNT(*)数行，COUNT(stock)只数stock非NULL的行，SUM求和，AVG求平均，MIN/MAX取最小/最大。

四个价格3、5、8、4都已知，最小3、最大8，平均是(3+5+8+4)/4=5。除COUNT(*)外，这些常见计算会忽略相应列的NULL；不要把未知库存当0参与平均。

SELECT COUNT(*) AS total FROM products;
SELECT MIN(price), MAX(price) FROM products;
SELECT SUM(stock), AVG(price) FROM products;

AS给结果列起别名，不修改原表列名。可先用WHERE筛选参与统计的行；库存为0的商品仍是一行，COUNT(*)会计数。没有匹配行时COUNT返回0，SUM/AVG通常返回NULL。本日用单组统计，按名称分组留到第8天。

04理解自测

用自己的话回答，再对照参考解释。

1 / 联合索引(name,price)为什么不能当两棵单列索引？

查看参考答案

它先按name分组，再在组内按price排序。只给price时通常没有同样的最左定位；WHERE条件的书写顺序不会改变索引列顺序。

2 / LIKE 水%与%水%的普通索引定位有何不同？

查看参考答案

前者给出开头，可能形成范围；后者开头未知，通常不能形成同样的B+树范围。后者仍可能扫描覆盖索引，不能说任何索引都绝不使用。

3 / LIKE '水%'与'%水%'筛出结果后，为何还要看候选范围？

查看参考答案

水%给出开头，可定位水、水果的前缀候选；%水%开头未知，本例检查四项再过滤出水、水果、饮用水。最终结果与访问范围不同，不能只看筛选成功就认为跳过了无关项。

4 / 索引路径要检查4项并回表4次，扫描只检查4行，为什么可能选扫描？

查看参考答案

索引能用不等于代价更低。它还要回表取缺失列；本例抽象工作更多。真实优化器依靠页访问、统计与缓存等估计，并不是数这四行就决定所有计划。

5 / EXPLAIN的rows等于查询返回的行数吗？

查看参考答案

不等于。它是估计检查的行数，可能与实际不同。COUNT(*)才对符合条件的行统计数量；计划候选possible_keys也不代表最终key。
