01

先认识数据库、表与SQL

小店要记录商品名称、价格和库存。只把这些信息写成一大段文字，程序就很难准确回答“哪些商品已经没库存”。把数据按规则组织起来，再提供查找和修改的能力，数据库系统就能帮助处理这些问题。

数据库

有组织的数据集合。这里可以有商品表、订单表等数据。

MySQL

数据库管理系统：管理和操作数据库的软件。它不是某一张商品表。

SQL

向数据库表达操作的语言，例如查询商品。它不是MySQL软件本身。

表中的一行和一列，各表示什么？

把商品组织成表，表名叫products。一行是一条商品记录；一列表达一种属性。四列分别是id编号、name名称、price价格和stock库存。列名告诉你“这一类值是什么意思”，格子里的值属于具体的一行。

例如，编号2这一行记录“面包、价格5、库存6”。想查看这一件商品，是选择行；只想看名称和价格，是选择列。筛选行和选择列可以同时进行，但都不会因为查询而删除原来的数据。

“关系型”首先指数据模型，不是两表间的箭头

关系模型用“关系”组织记录，入门时可以用表理解：各行按同一组列表达属性。把两张表关联起来是它能做的事情，但不是名称的全部含义。即使只有一张表，或者没有声明外键，也可以使用关系型数据库。

表和查询结果也要分开。

商品表保存原有记录；查询可以返回其中几行、几列组成的结果。没有指定排序时，不能把结果碰巧出现的顺序当成保证。

小检查：查出面包的价格，改变了商品表吗？

没有。读取并返回price的值，不等于修改price。修改数据要用另一类语句，后面再学习。

02

关系型与非关系型：数据怎样组织

关系型与非关系型的定义

数据模型，就是组织和表达数据的一套规则。用表记录商品，就是一种组织方式。数据库按主要采用的数据模型，分为关系型与非关系型。

关系型数据库

以关系模型组织数据的数据库。入门时可以把“关系”理解为表：一张表用共同的列描述记录，每一行是一条记录。MySQL是常见的关系型数据库。

非关系型数据库

不以关系模型作为核心数据模型的数据库的总称。它们可以主要用文档、键值或图等方式组织数据。因此，“非关系型”不是一种单独的模型。

关系型：用表记录商品

回到products表：先约定id、name、price、stock四列，再让每条商品记录按这套结构填写不同的值。例如，“水”和“面包”都有名称、价格和库存，我们可以用同一条查询找出库存为0的商品。

非关系型的常见模型

常见模型怎样组织数据一个小例子
文档
例如MongoDB		把一条记录组织成一份带字段的文档。这里的“文档”不是Word文件，而是一份结构化记录。商品1：编号、名称、标签；商品2：编号、名称、重量。
键值
例如Redis的常见用法		通过一个键找到对应的值。键相当于查找用的标识，值是它对应的数据。product:1 → 水，用product:1找到“水”。
图用节点表示对象，用边表示对象之间的联系。“小李”和“商品1”是两个节点，“购买”连接它们。

表中的列和文档中的字段都能表达属性，比如name表示名称。两份商品文档可以带不同的附加字段：tags表示标签，方括号中的多个标签是一份列表，也叫数组。

能灵活表达，不等于没有任何规则

两份文档可以有不同的附加字段，但文档数据库也可以检查数据是否符合约定。部分系统还支持事务，即把一组操作作为一个整体处理；后面会专门学习。关系型数据库也能支持文档式的数据。分类看主要数据模型，不是看它能不能提供某一项功能。

数据模型不等于性能结论。

是否更快、有哪些规则、怎样支持事务，要看具体系统和使用场景，不能只凭分类下结论。

关系型与非关系型的核心区别是什么？

关系型以关系模型组织数据，通常用表理解，例如MySQL。非关系型是其他数据模型的总称，例如MongoDB的文档模型；不是统一的“更快的表”。

03

键：认出一行，再找到关联

键的含义与四个核心概念

在表的设计中，键是用来识别记录或表达引用关系的一列或一组列。“一组列”可以只有一列，也可以由多列组合而成。它不是键盘上的按键，也不是把某个字段的名字改成“key”。

超键、候选键、主键围绕“怎样唯一识别本表的一行”，外键围绕“这一行引用了什么”。它们不是四选一的关系，同一组列可以同时符合多个定义。

概念定义回答的问题
超键能唯一识别一行的列或列组合。这些列合起来，能认出是哪一行吗？
候选键不能再删掉任何一列的超键。能认出一行，而且没有多余列吗？
主键从候选键中选来作为表的主要标识的键。这张表正式选哪一个标识？
外键按声明的引用规则，引用另一张表或本表中相应键的列或列组合。这条记录引用了哪条记录？

键还有其他称呼。例如“联合键/复合键”表示一个键由多列组成，它也可以是主键。

商品表中的键

商品1和商品4都叫“水”，所以只凭name不能准确区分。我们在设计时约定id唯一且不能为空，用编号识别商品。下面的例子都以这条设计规则为前提，而不是靠四行样本碰巧没有重复来猜。

记号{id, name}表示把id与name两列合起来考虑；花括号是这里解释列组合的记号，不是要执行的SQL。

1. 超键：能唯一识别记录

本例中{id}能找到一件商品，是超键。{id, name}也能找到，因为id本身已经唯一；它虽然多带了name，仍符合超键的定义。

2. 候选键：没有多余列的超键

{id}符合；{id, name}不符合，因为删掉name，剩下的id仍能唯一识别商品。候选键的“最小”指不能再删列，不是只允许所有候选键中列数最少的那一个。

3. 主键：选定的主要标识

本例选id作为商品表的主键。因此id既是超键，也是候选键，同时又是选定的主键。一个表至多声明一个主键，但这个主键可以包含多列；主键各列都不能为NULL。

前三种键的关系：能识别 → 去掉多余列 → 选定主要标识。

所有候选键都是超键，选定的主键是候选键之一。不要把它们当成互不相干的三类字段。

4. 外键：引用另一条记录

“约束”是要求数据遵守的规则；“参照约束”就是检查引用关系的规则。订单101购买商品1，我们既要识别“哪张订单”，也要知道“买了哪件商品”。

orders是订单表，orders.id表示它自己的订单编号；orders.product_id表示订单中记录的商品编号；quantity表示购买件数。若声明product_id引用products.id，这里的product_id就是外键。它不是订单自己的主键，而是在引用商品。

多条订单可以买同一件商品，因此外键的值可以重复：订单101和102都可以填product_id=1。

约束要声明，不能靠猜。

声明并启用外键检查时，引用不存在的商品会被拒绝。没有外键声明时，数据库不会自动补上这一业务规则。NULL表示缺失或未知的值，不等于0或空字符串；外键本身不自动禁止NULL，如果订单必须有商品，还需另外要求该列不能为空。

订单编号和商品编号恰好相同，是外键吗？

不是看数字碰巧相同。要看设计中谁引用谁，以及是否声明了相应约束；orders.id用于识别订单，orders.product_id才是这里引用商品的列。

04

字段类型：怎样解释一个值

字段名与字段类型

字段就是表中的列。例如name是字段名，告诉你这一列表示商品名称。字段类型则约定这一列的数据怎样表示和处理：名称是文字，库存是整数，日期是时间信息，不能只看字段名来决定类型。

比如给库存取名stock，并不自动让它成为整数类型；设计表时还要为它选择类型。

常见类别用来表达什么类型示例
数值库存10这样的整数，或金额8.50这样的精确小数。INT：整数
DECIMAL：精确小数
字符串名称“牛奶”、代码“AB”等文字。字符串就是一串字符。CHAR、VARCHAR
TEXT也是文本类型
日期与时间某一天，或包含时分秒的日期时间。DATE：日期
DATETIME：日期时间
二进制数据图片等文件的原始内容，而不是图片文件名这串文字。BLOB：二进制数据

上表列出常见类型，不是完整类型清单。商品的id、stock可用整数类型；name需要字符串类型。本课练习用整数价格简化，实际金额通常选DECIMAL等合适的精确数值类型。

CHAR与VARCHAR：固定长度与变长字符串

CHAR和VARCHAR都属于字符串类型，区别在于怎样处理字符串长度。

CHAR(n)：固定长度字符串

按声明的长度处理字符串。例如CHAR(4)按4个字符的长度处理；写入短值时会补空格到这个长度。

VARCHAR(n)：变长字符串

保存实际内容并带上长度信息，n规定内容最多有多少个字符。例如VARCHAR(4)不需要因为声明4，就把每个短值都补成4个字符。

两者括号里的n都是字符数，不是字节数。字符是“猫”、字母“A”这样的文字单位；字节是存储信息的计量单位。字符如何编码成字节，要看字符集，因此不能把每个汉字固定算成两个字节。

例：写入两个字符“AB”

CHAR(4)补两个空格；VARCHAR(4)保存AB这两个字符和相应长度信息。VARCHAR存的是内容，不是只存一个指针。

长度、取回、比较，不要混为一件事

默认取回时，CHAR的尾部空格会被去掉；VARCHAR通常保留合法长度内的尾空格。字符串比较是否忽略尾空格，又与排序规则有关；排序规则就是系统比较文字时使用的规则。超长值如何处理还受SQL模式等条件影响，不能一概说会安静地截掉。

不要背“CHAR一定更快”。

固定和变长是类型的基本区别；真实空间、比较行为和性能还要看字符集、存储引擎、数据与查询。名称长短变化较多时，VARCHAR是常见选择，但这不是通用性能结论。

VARCHAR(4)能否理解为最多4字节？

不能。它限制的是字符数，实际字节受字符集影响。另外还要考虑长度信息与整行大小等限制。

03SQL短练习

选列与筛选行

SELECT说明要哪些列，FROM说明从哪张表取，WHERE说明哪些行符合条件。星号*表示所有列；列之间用逗号分隔，字符串值用单引号包住。

SELECT name FROM products;

从商品表取所有记录的名称。

SELECT name FROM products WHERE price = 3;

只取价格等于3的记录，再返回名称。=表示等于，>表示大于；WHERE在这里筛选行，不修改数据。

关键字大小写通常不影响这里的写法；建议保持一致。本课表名和列名按下方数据表书写，先不用排序和复杂条件。

04理解自测

先用自己的话回答，再展开参考答案。

1 / MySQL、SQL和商品表，是同一种东西吗？

查看参考答案

不是。MySQL是管理数据库的软件；SQL是表达查询和修改的语言；商品表是被管理的一部分数据。程序用SQL让MySQL对表进行操作。

2 / 两件商品都叫“水”，怎样准确引用其中一件？

查看参考答案

使用设计时约定唯一且非空的商品主键，例如id。订单用product_id引用对应商品。商品名称可能重复，订单也不能只凭“水”来区分商品1和商品4。

3 / {id, name}为什么可以是超键，却不是候选键？

查看参考答案

本例约定id本身唯一，因此{id, name}也能识别一行，是超键。但删掉name后{id}仍能识别，所以它不是不可再删列的候选键。候选键的“最小”不是比较所有候选键的列数。

4 / VARCHAR(4)就是最多4字节，并且比CHAR慢吗？

查看参考答案

两种说法都不能这样下结论。4是字符数，实际字节看字符集；VARCHAR是变长、CHAR是固定长度，性能还取决于存储引擎、数据和查询。尾空格的取回与比较行为也要分开。

5 / 没有外键就不是关系型，非关系型一定没有事务，对吗？

查看参考答案

都不对。“关系型”首先指按关系组织数据的模型，不以是否声明外键来判断。非关系型有多种系统和模型，一些文档数据库也支持多文档事务；不能只凭分类否定其能力。
