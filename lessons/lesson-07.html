02今日主线

转账要把A的10元交给B。两条UPDATE分别成功，不等于整笔成功；把两步放进共同边界，才能在加款失败时撤销尚未提交的扣款。边界解决完整性，金额规则、并发读取与崩溃恢复还需要各自的保证。

01

转账失败与事务边界

A有100元，B有50元。转账10元要做两次修改：A = A - 10、B = B + 10。成功后应是90与60，总额仍为150；如果扣款成功、加款失败，就会只剩140。

事务是按同一个提交或撤销边界管理的一组数据库操作。BEGIN或START TRANSACTION明确开启事务；COMMIT提交确认修改并结束事务；ROLLBACK回滚撤销尚未提交的修改。普通InnoDB表支持这些事务性修改，第3天的引擎选择决定能否依靠这种保证。

MySQL默认开启自动提交：没有显式事务时，每条成功语句各自提交。左栏的扣款因此立即确认；右栏已BEGIN，扣款仍未提交。加款失败后，两栏看见的余额相同，但撤销边界不同。

共同事务的正常成功路径是：BEGIN → A扣10 → B加10 → COMMIT，最终A90、B60，总额150。加款失败时，程序明确执行ROLLBACK，不留下半笔修改；这种整体成功或撤销的保证叫原子性。报错本身不保证整笔回滚，连续写两条SQL也不会自动建立共同业务边界。

02

回滚能撤销到哪里

COMMIT结束事务，之后的ROLLBACK不能撤销它。 修正已提交误扣，需要新的更正操作或恢复方案。

报错与DDL边界

语句报错不总意味着整个事务自动回滚，程序要明确处理。普通DROP、TRUNCATE等DDL会隐式提交，不能像本课UPDATE一样理解为提交前可撤销。

03

整体执行与业务正确

现在两步都成功，也在一个事务里提交。如果程序把“加10”写成“加20”，事务会替你纠正吗？数据库可以保证这两步整体处理，但数据库不知道所有业务规则。

这里需要区分原子性与一致性（Consistency）：前者保证修改整体成功或撤销；后者要求事务前后都满足数据规则。本例的规则是总额150不变。主键唯一等规则可由数据库约束检查；转账金额的对应关系还依赖正确程序。原子地执行错误程序，仍会得到错误业务结果。

事务的四种性质合称ACID，不是四个依次执行的阶段：

  • A，原子性：半做的扣款能否随整笔失败撤销？
  • C，一致性：做完后，总额等规则是否仍然成立？
  • I，隔离性：多人同时操作时，彼此可以看到什么、怎样互相影响？
  • D，持久性：已经确认的结果，在承诺的故障与配置条件下能否保住？

扣款后的临时总额140不代表最终业务状态；一致性不能简化成“每一条中间SQL执行后，所有业务规则都已满足”。真正要判断的是整笔事务结束后是否仍符合规则。

04

事务在MySQL系统中的位置

把事务接回第3天的服务器：服务层理解并执行BEGIN、UPDATE等命令；InnoDB在存取记录时管理本事务的修改与状态。BEGIN开启，UPDATE暂改，COMMIT确认并结束，或ROLLBACK撤销未提交修改并结束。事务不是执行完SQL才额外经过的一站，它的状态伴随这些操作。

共同边界没有替程序决定所有并发规则。两个程序都普通读取库存10，各算9；A执行UPDATE products SET stock=9 WHERE id=1;并提交，B随后也写9并提交。第二次写的是旧读数算出的同一个绝对值，不是“在现在库存上再减1”，最终仍为9，只扣一次。这叫丢失更新，各自提交成功仍不足以保证业务扣两件。

第8天展开别人能读到什么，第9天比较原地条件扣减，第10天再看锁定或版本检查。它们针对不同问题，不能只回答“加BEGIN”。本地ROLLBACK也不会撤回已发短信或外部支付，这些动作需要另外处理。

03SQL短练习

提交或撤销库存修改

把转账中的“确认或撤销”换成一条库存修改，语法边界相同。每题只补一条短SQL，数据恢复后再做下一题。

BEGIN;
UPDATE products SET stock = 8 WHERE id = 1;
COMMIT;

BEGIN开始事务，UPDATE暂改库存，COMMIT确认；把末行换成ROLLBACK，库存回到修改前。第1、2题补事务结尾；第3、4题补UPDATE，再观察预设结尾。结果保留整张小表，检查有没有改错行。

SQLite离线练习，不是MySQL机制实验。

每题在独立SQLite数据库中执行已展示的事务步骤。只练BEGIN、COMMIT、ROLLBACK与短UPDATE；不用于验证MySQL的并发隔离、日志或锁。

04理解自测

用自己的话回答，再对照参考解释。

1 / 自动提交下只扣未加，与同一事务中失败回滚，最终余额为什么不同？

查看参考答案

起点100与50。自动提交的扣款已确认，回滚后仍90与50；同一未提交事务中的扣款可撤销，恢复100与50。差别是共同的确认边界，不是SQL是否连续书写。

2 / 扣10、加20在同一事务提交，原子性与业务一致性能否同时成立？

查看参考答案

修改可以整体提交，但总额变160，违反总额150的规则。原子地执行不等于业务正确；一致性还依赖正确程序和适当约束。

3 / 余额是90，怎样判断ROLLBACK能否恢复100？

查看参考答案

看扣款所属事务是否仍未提交。BEGIN之后尚未COMMIT可回滚；已经COMMIT或默认自动提交的成功修改不能靠后来的ROLLBACK撤销。

4 / 两个程序都先读库存10，再各自写9并提交，为什么只扣一次？

查看参考答案

两人把同一个旧读数算成绝对值9，后次又写9，没有表达在当前值上再减1。最终仍9，只扣一次；各自提交保证不了这段并发业务正确，后面还需展开更新方式与协调。

5 / 第二条SQL报错，是否等于整笔业务和已发短信都被撤销？

查看参考答案

不等于。错误不总自动回滚整个事务，程序要明确处理；短信等外部动作也不会自动随本地数据库ROLLBACK撤销。
