02今日主线

01

字段类型、约束与建表

字段类型规定一列保存哪类值，例如整数或字符串；约束是数据库检查数据必须满足的规则。只有INT类型，还不能表达“商品编号不重复”或“库存不能小于0”。这些要求要另外声明。

常见规则含义小例子
NOT NULL不允许缺少值。NULL表示没有已知值，不是0或空字符串。商品名称必须提供。
UNIQUE不允许重复的非NULL键值。商品条码不能重复。
PRIMARY KEY选定用于识别行的键，值唯一且非NULL。每件商品有独立编号。
FOREIGN KEY按声明的规则检查引用关系。订单引用的商品编号必须存在。
CHECK检查指定条件；MySQL中条件为FALSE（不成立）时拒绝写入。要求库存不小于0。

一张表的定义

CREATE TABLE创建表，括号内用逗号分隔列定义和表级规则：

CREATE TABLE products (
  id INT PRIMARY KEY,
  name VARCHAR(20) NOT NULL,
  price INT NOT NULL,
  stock INT NOT NULL CHECK (stock >= 0)
) ENGINE = InnoDB;

这里用整数价格简化数据；真实金额通常会考虑DECIMAL等合适类型。ENGINE = InnoDB指定负责存取数据的存储引擎，内部机制留到后续课程。建表成功时只有定义，商品记录仍需插入。

规则各管一件事

NOT NULL不保证名称不是空字符串；MySQL的UNIQUE允许可空列出现多个NULL。CHECK (stock >= 0)遇到NULL不算FALSE，所以需要和NOT NULL配合。普通插入违反这里的主键或必填规则会报错，不会自动替你修正。

约束检查“这条数据是否合规”；范式检查“这些信息放在同一张表是否合适”。即使每个编号都合法，表的组织方式仍可能造成重复维护。

02

第一范式：一个字段表达一个值

范式是关系表设计应满足的一组条件。三大范式逐层增加要求：1NF检查一个字段是否塞进多个需要分别处理的值；2NF检查某项信息是否只由组合键的一部分确定；3NF检查某项信息是否通过另一项非键信息间接确定。

第一范式（1NF）要求每个字段取一个原子值，而不是一组需要分别处理的值。“原子”表示在当前数据模型中作为一个整体使用，不是说文字不能再拆成字符。

例如，订单101买了商品1和2，把product_ids写成1,2，查询“谁买了商品2”就需要拆清单。改成订单明细，每行保存一个订单编号和一个商品编号，就能直接用WHERE product_id = 2筛选。

同一个订单编号出现在多行不违反1NF：这里一行代表一条订单明细，而不是整个订单。商品名称“牛奶”作为一个名称使用也不需要拆字。不能只凭“没有重复列名”判断1NF，也不能因为MySQL允许保存JSON，就说它不是关系型数据库。

03

第二范式：信息要依赖整个键

函数依赖描述列之间的确定关系：按业务规则，确定A的值，就能确定B的值，写作A → B。例如，每个商品编号对应一个当前名称，因此product_id → product_name。名称可能重复，所以反过来未必成立。这是设计规则，不是从几行样本的巧合推断出来的。

订单明细约定：同一订单中，同一商品最多一行。只有同时知道order_id和product_id，才能确定购买数量quantity。两列一起组成候选键；单独一列都不能识别明细，这称为组合键。不属于任何候选键的列，称为非主属性。

在这个设计中，数量依赖整个组合键，是完全依赖；商品名称只依赖其中的商品编号，是部分依赖。如果每条明细都再写一次商品名称，名称修改就要更新多行；漏改一行，商品1就会同时叫“水”和“饮用水”。

第二范式（2NF）在满足1NF的基础上，要求每个非主属性都完全依赖每一个候选键，没有部分依赖。本例只有一个候选键，部分依赖就是“只需要组合键的一部分，就能确定该列”。

拆成products(product_id, product_name)与order_items(order_id, product_id, quantity)后，名称按商品编号维护一份，数量仍属于具体明细。两表保留product_id，之后可据此关联，不是把联系丢掉。

若所有候选键都只有一列，就不会有这里的部分依赖。只看“主键是一列”不够，还要考虑其他候选键；增加一个自增编号也不自动消除已有的业务依赖。

04

第三范式：类别名称属于类别

商品表每行都有唯一商品编号，却仍可能重复记录类别名称。约定每件商品属于一个类别，每个类别编号对应一个名称：product_id → category_id，并且category_id → category_name。于是商品编号通过类别编号间接确定类别名称，这叫传递依赖。类别编号不能识别商品，不是商品表的键。

第三范式（3NF）在满足2NF的基础上，排除非主属性对候选键的不合适传递依赖。在本例中，类别编号与类别名称都是非主属性，类别名称依赖的不是商品本身，而是它所属的类别。

这会产生三种常见的数据维护异常，即信息难以独立、正确地修改：

  • 更新异常：“饮品”改名为“饮料”，必须修改该类别的每一件商品，漏改会不一致。
  • 插入异常：想记录一个尚无商品的新类别，却必须先凑出一条商品记录。
  • 删除异常：删除该类别的最后一件商品，也把唯一的类别信息一起删掉。

把类别名称移到categories(category_id, category_name)，商品表只保存类别编号，就能独立维护类别。关联需要的编号仍保留；拆表的目的不是让列数尽量少，而是让事实放在合适的位置。

3NF的更一般判定

对于一条非平凡函数依赖X → A，即A尚未包含在X中，3NF要求X是超键，或者A属于某个候选键。这里的类别编号不是超键，类别名称也不属于任何候选键，因此违反3NF。这条判定避免把复杂的多候选键情况简化成“所有列只能依赖主键”。

三大范式解决的是三种问题

1NF不把多个商品编号塞进一个字段；2NF不把商品名称附在每条组合键明细上；3NF不把类别名称附在每件商品上。减少重复维护不等于完全没有重复值，也不保证查询一定更快。拆表后可能需要关联查询；为了性能保留冗余时，也必须设计好一致性维护方式，不能单凭“表越多越规范”作决定。

05

删几行、清空数据、删除表

表结构是表名、列和约束等定义；表数据是其中的记录。删除商品1、清空全部商品、不要商品表了，是不同的要求。

操作数据与结构能否筛选行MySQL/InnoDB中的回滚
DELETE FROM products WHERE id = 1;删除符合条件的行，保留表结构。可以用WHERE；省略就删所有行。未提交的事务内可以回滚。
TRUNCATE TABLE products;清空全表，保留可用的表定义；重置自增计数。不能加WHERE。引起隐式提交，不能用用户ROLLBACK撤销。
DROP TABLE products;删除表定义和数据，表不存在了。不是按行删除。普通表的删除引起隐式提交，不能用用户ROLLBACK撤销。

自增编号由数据库按计数生成，MySQL用AUTO_INCREMENT声明；它不是“删除一行就重新编号”。上面的建表示例没有声明自增，插入时需要自己提供id。

事务是一组按整体管理提交或撤销的操作；COMMIT提交，ROLLBACK撤销尚未提交的修改。MySQL默认开启自动提交：一条成功的DELETE通常已自动提交，之后再写ROLLBACK也不会把它找回来。

隐式提交表示语句本身会触发提交，不需要你另外写COMMIT。DELETE属于操作数据的DML；TRUNCATE和DROP属于操作定义的DDL。这些简称用于区分操作性质，不是“危险程度排行榜”。

TRUNCATE通常比逐行删除更适合快速清空大表，但外键引用等条件可能使它不能执行；它不触发DELETE触发器，即预先定义的删除响应动作。不能背成“任何时候都更快”或“完全没有日志”。DELETE也不保证重置自增编号。需要删部分记录，就明确写WHERE；需要撤销机会，还要在事务提交前处理。

03SQL短练习

增加一行，修改值，删除一行

INSERT INTO products (id, name, price, stock)
VALUES (5, '茶', 6, 3);

INSERT INTO指定表和列，VALUES提供对应的值。列与值按位置一一对应；字符串用单引号。明确列清单，不依赖记住表的物理列顺序。

UPDATE products SET stock = 7 WHERE id = 2;

UPDATE指定要改的表，SET指定新值，WHERE限定目标行。没有WHERE时会修改所有行；改多列时用逗号分隔，如SET price = 6, stock = 7。

DELETE FROM products WHERE id = 3;

DELETE FROM删除符合条件的整行，不是把某一列变空。日常操作可先用相同WHERE条件做SELECT，确认目标记录，再执行修改或删除；这不能替代事务与并发控制。

练习使用SQLite，不连接真实业务数据。

四题各自从下方四行数据开始，每次运行自动恢复，不需要连续完成多条语句。增删改成功后显示整张表，方便检查有没有误改其他商品。这里只练通用语法，不实验MySQL的TRUNCATE、隐式提交、外键或存储引擎。

04理解自测

用自己的话回答，再对照参考解释。

1 / id写了INT，是否就能保证编号不重复？

查看参考答案

不能。INT规定类型，PRIMARY KEY或适当的唯一约束才检查唯一性。主键还要求非NULL；名称的NOT NULL也只是禁止缺失值，不是禁止空字符串。

2 / 商品编号清单“1,2”和商品名称“牛奶”，为什么不需要同样拆开？

查看参考答案

编号1、2需要分别筛选和引用，是两个需要独立处理的值，应放到明细行。名称作为一个整体使用，不需要拆成字符。1NF的原子性取决于模型中的使用方式，不是文字能否再拆字。

3 / 明细的候选键是(order_id, product_id)，商品名称和购买数量分别依赖什么？

查看参考答案

按本课业务约定，名称只依赖product_id，是对组合候选键的部分依赖；数量要由整个组合键确定。把当前商品名称移到商品表，明细保留商品编号和数量，就消除了这处2NF问题。依赖依据业务规则，不靠样本碰巧唯一。

4 / 商品表已有单列主键，为什么类别名称仍可能需要移到类别表？

查看参考答案

商品编号确定类别编号，类别编号又确定类别名称，形成不合适的传递依赖。类别名称重复维护会造成更新、插入和删除异常。类别表独立保存编号与名称，商品表保留类别编号供关联；单列主键不等于满足3NF。

5 / DELETE、TRUNCATE、DROP能互换吗？DELETE执行后一定能回滚吗？

查看参考答案

不能互换：DELETE删行并保留表，TRUNCATE清空全表并重置自增计数，DROP删除普通表的定义和数据。MySQL/InnoDB中，DELETE需要处于尚未提交的事务内才有回滚机会；默认自动提交后不能再撤销。TRUNCATE和普通表DROP会隐式提交，不能用用户ROLLBACK撤销。
